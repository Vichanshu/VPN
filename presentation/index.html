Detecting VPN use with device fingerprinting and network measurements

What the system collects, how it recognises a device across browsers, and how it decides whether a connection goes through a VPN.

Deep Learning Lab · research prototype · built with Next.js and PostgreSQL

The problem and the goal

Problem

  • Organisations that verify identity or location see only an IP address.
  • A VPN, proxy or relay replaces that address, so the location and network can be false.
  • IP lists alone miss new, small or residential VPNs.

Goal

  • Recognise the device, not just the address.
  • Decide how likely it is that a visit comes through a VPN, with reasons.
  • Use only what a website legitimately sees: the request, the browser, and past visits.
Core idea. A VPN changes the network a device appears from, not the device itself. Once we know the device, its own history becomes the baseline.

The output is a research probability, not proof. It needs calibration on labelled data before any production use.

Two applications, one database

System architecture, start to end

What happens during one visit

  • The collector waits for the page to finish loading, then measures latency first, because fonts, hydration and GPU timing probes would inflate it.
  • It then waits up to 4 seconds for about 40 mouse movements, which the pointer-rate signal needs. If none come, the scan continues without it.
  • The signed challenge ties the scan to the IP and time it was issued, so a scan cannot be replayed later.
  • Location is asked through the normal browser prompt. If the visitor declines, the scan continues without it.
  • Anti-abuse: size limit (300 KB), rate limit per IP, and strict input validation on every field.

Part A. What makes one browser recognisable

No single value identifies a browser. Many small values, taken together, usually do.

Entropy

How rare a value is. A screen size of 1920×1080 is common. A specific GPU model plus a long font list is rare.

Stability

How often the value stays the same between two visits of the same device. A browser update changes some values and not others.

Collision

How often two different devices share the value. Collision is higher on phones, where models are identical.

How the system treats each parameter

  • Every parameter has an expert prior for stability and collision, per operating system (about 45 parameters, schema 5.1).
  • Values are compared in four bins: exact, close, partial, different. Close values count for something, so a version bump does not break the match.
  • Raw pixels, audio samples and positions are never sent. The browser sends hashes, buckets and short summaries.
  • The prior is later replaced by counts from our own labelled data (Part B).

Parameters 3. Installed assets and hardware timing

Operating-system assets

  • Fonts: 170 font names tested with canvas text measurements.
  • Emoji: which Unicode release the emoji font supports, plus glyph widths.
  • Writing systems: 36 scripts checked for glyph support.
  • Voices: local speech-synthesis voices (opt-in).
  • Defaults: generic-font metrics and CSS system colours.

These follow the OS image, so they are strong for device identity but correlated with each other.

Hardware timing probes (experimental)

  • GPU execution-unit timing (DrawnApart, NDSS 2022): time a draw loop at 16 points, 7 rounds, compare the profile by correlation.
  • WebGPU scheduling (AtomicIncrement, WiSec 2025): order of atomic tickets across workgroups.
  • Refresh rate from animation frames, pointer rate from coalesced pointer events.

Timing is weak and noisy. The model caps its whole family at +2 / −1.5 log-odds and ignores traces that fail.

When browsers hide or fake values

Protection detection

  • Brave, Firefox private mode and Safari add noise or mask the GPU name.
  • Tests: solid-colour canvas read-back, rendering twice and comparing, masked WebGL strings, known browser flags.
  • Rule: a randomised feature is excluded, not penalised. It simply does not vote.
  • If too little remains, the answer is "not enough data" instead of a guess.

Consistency checks

  • JavaScript user-agent against the HTTP header the server saw.
  • Client-hint platform against the parsed operating system.
  • A mismatch means the fingerprint may be spoofed, and it is recorded as a note.
Source ideas: FP-Inconsistent (2024/25), FP-Scanner (USENIX Security 2018).

Part B. Recognising one device across browsers

Chrome and Firefox on the same laptop render differently, but the laptop is the same. So each parameter is tagged with how far it travels.

How two scans are compared

  • Ratios are learned. Each bin's probability is a blend of the expert prior and counts from labelled pairs in our own data. The model works from scan one and becomes data-driven as labels grow.
  • 13 feature families (platform, model, defaults, hardware, display, GPU, GPU timing, OS assets, locale, audio hardware, engine rendering, browser config, network), each with its own positive and negative cap.
  • Calibration. Platt scaling with a prior-shift correction switches on automatically at 25 same-device and 25 different-device labelled pairs.
  • Pairs with too little shared evidence never link, whatever the percentage.

Grouping scans and training the model

Same-device sets

  • Every scan is compared with every other scan once.
  • A scan joins a set when the model is at least a chosen percentage sure (default 85%) that it is the same device as one of its three closest matches.
  • "Mutual closest match" option also joins two scans that are each other's best match above 50%.
  • Method: FP-STALKER style, with union-find so membership is consistent.

On each scan in the admin

  • A list of the other scans it looks like (at least 50%), with the probability and each one's VPN percentage.
  • "Unique" when nothing else matches.

Training the model

  • Leave-both-devices-out: a pair is scored with counts that exclude both of its devices, so the model never sees the answer.
  • Public visitors never train it. They have no real device name, so one laptop in two browsers would be counted as two devices. They are scored by the model, not used to build it.
  • The dashboard shows no linking-accuracy scores. Compare any two scans to see the reasons behind a match.
Important. Scores trust device names typed by people. If one device is saved under two names, correct links count as mistakes. Use one name per physical device.

  • Browser and engine differ, so canvas, audio and WebGL hashes did not vote.
  • OS, screen, timezone, language, GPU family and the shared network voted.

How to read it

  • The admin lists each scan under "Similar devices" with that percentage.
  • 70.7% is below the 85% set threshold, so they are shown as similar but not merged.
  • More scans of the same device raise confidence, and Firefox masks the exact GPU model.

Part C. Detecting a VPN

Idea. Gather several independent kinds of evidence, give each a weight, and combine them. No single signal decides, and each group is capped so correlated signals cannot dominate.
GroupSignalsWhere it comes from
Time and latencyTimezone mismatch, latency too large for the IP's location, impossible location, app vs TCP gapBrowser clock, round-trip timing
Network identityVPN, datacenter, Tor and relay lists, IPinfo privacy flags, network owner namePublic lists, IPinfo
Location truthRIPE Atlas probe pings, device location from the browserRIPE Atlas, browser
LeaksWebRTC address differs from the HTTP address, forwarding headersSTUN, request headers
Device historyDevice left its usual network, slower than usual, new countryLinkage model (Part B)

Time difference 1. Browser clock against IP location

  • Offsets differ by at least 60 minutes: +2.0. Offsets equal: −0.5.
  • The original prototype's main rule. It is now one signal among many, because travellers and VPN users near their own country will not trigger it.
  • When the IP location is unknown, a related rule applies: if the nearest landmark by latency is far from where the browser timezone suggests, the connection is flagged.

Time difference 2. Application delay against TCP delay

Needs the server's TCP round-trip time from a trusted front end (for example nginx $tcpinfo_rtt passed as a header). Vercel does not supply it, so this signal is optional and off by default.

Pinging servers. Is the IP where it claims to be?

Method

  • The browser pings 12 cloud regions with known coordinates: Mumbai, Hyderabad, Singapore, Tokyo, Sydney, UAE, Frankfurt, London, N. Virginia, N. California, São Paulo, Cape Town.
  • One warm-up request each, then the fastest of 3 samples. About 2 seconds.

Rules (light in fibre ≈ 100 km per ms of round trip)

  • Excess latency = min over landmarks of (RTT − distance / 100).
  • Excess > 180 ms: +2.4. > 100 ms: +1.3. < 50 ms: −0.9.
  • Impossible location: a landmark over 1,500 km away answers faster than light allows for the claimed place: +1.6.

Lists are downloaded by the server, cached 24 hours, and searched locally with binary search over merged ranges (IPv4 and IPv6). No visitor IP is sent anywhere.

Free location from Vercel

Vercel adds country, region, city, latitude, longitude and timezone headers to every request, so IP geolocation needs no outside service.

Leak and header checks

  • WebRTC: the browser asks a STUN server for its public address. If it differs from the address the server saw (same IP family): +2.7.
  • Forwarding headers (Via, Forwarded, X-Proxy-ID): +1.5.
  • Idea: VPNalyzer (NDSS 2022) found leaks in many VPN clients.

IPinfo. A second opinion on the address

What IPinfo returns

  • Privacy flags: vpn, proxy, tor, relay, hosting (on plans that include them).
  • ASN, network owner, network type, claimed city and coordinates, anycast flag.

The token travels in an Authorization header, never in the URL or a response.

RIPE Atlas. Probes around the world ping the address

  • Ping the target from 4 probes within 150 km of the claimed place and from far probes in 8 countries (US, BR, GB, ZA, IN, SG, JP, AU). Up to 12 probes, 2 pings each.
  • Verdicts: consistent (−1), inconsistent (+3), inconclusive (no vote).
  • It costs credits, so it runs only when cheaper layers are unsure (likelihood between 20% and 85%), at most 20 measurements per day, and measurements stay private.
  • It is asynchronous: the result arrives later and applies when the scan is re-scored.

Combining the evidence into a percentage

Example: probably a VPN
datacenter list +2.8, device left its usual network +1.4, slower than usual +1.0 = +5.2. Add prior −2.94: total +2.26, so 90.5%, high.
Example: probably not
ordinary ISP −0.7, timezone matches −0.5, on its usual network −1.0 = −2.2. Add prior: total −5.14, so 0.6%, low.

Weights are log likelihood ratios from the literature and judgement. They are not fitted to our data yet.

Read with care

  • Only 8 VPN scans, so the sample is small.
  • Everyone shared one campus or mobile network, which makes "left its usual network" unusually clean.
  • Timezone, landmark and WebRTC signals were added after these scans, so they are not in these numbers.
  • VPN exits near the user, Opera's built-in VPN, residential proxies and corporate VPNs are the hard cases. Lists and device history are the fallback.

The admin dashboard

Visitor scans are tagged public-visitors and are scored by the same model as lab scans, but are left out of its training. Earlier archived scans are shown and scored, but are never linked to new ones.

Privacy, consent and data handling

Built in

  • Location only through the browser's own permission prompt, and the scan works without it.
  • Visitors are identified only by a random id stored in their browser, not by name.
  • Raw pixels, audio and positions are never stored. Only hashes, buckets and summaries.
  • Fingerprint components are also stored as server-side HMACs.
  • Visitors never see the verdict.
  • Raw observations can be deleted on a schedule (default 30 days) through an authenticated endpoint.

Needs a decision before going live

  • Informed consent text and a privacy notice that match what is collected.
  • Ethics or institutional review approval for collecting from public visitors.
  • Legal review: GDPR and ePrivacy Article 5(3), India's DPDP Rules 2025.
  • A fingerprint links a device, not a person, and a score is never proof of VPN use.
  • Admin access control and a data-retention period.

Limits and next steps

Known limits

  • JavaScript values can be changed or replayed. They are not attestation.
  • Privacy browsers add noise, so some evidence is missing.
  • Identical, identically imaged machines are hard to tell apart.
  • Weights are research estimates, not calibrated probabilities.
  • Packet-level methods (MTU, JA4T, protocol fingerprints) need network access a website does not have.

Next steps

  • Collect more labelled data: one name per device, several browsers, a private window, and VPN on and off.
  • Re-scan the same devices a week later to measure drift.
  • Fit the VPN weights on that data, then recalibrate.
  • Add a TCP RTT header behind a trusted front end for the CalcuLatency check.
  • Add admin login, then run the visitor site on real traffic.

Summary

  1. Collect a compact fingerprint, timing and network view of each visit, automatically.
  2. Recognise the device across browsers using device, engine and browser scopes and a calibrated likelihood model.
  3. Detect VPN use by combining time differences, landmark pings, IP lists, IPinfo, RIPE Atlas, leaks and the device's own history.
  4. Show the admin a VPN percentage and the similar devices for every visitor, with the reasons.
  5. Deploy as two small apps on one database, with secrets kept in the host.
Result so far. 8 of 8 labelled VPN scans caught and 0 of 64 false alarms on a small campus study. Larger, more varied data is the next test.
